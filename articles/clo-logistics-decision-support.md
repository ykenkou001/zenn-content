## はじめに

2026年度施行予定の規制的措置では、一定規模以上の荷主や連鎖化事業者などが特定事業者として指定されると、中長期計画の作成や定期報告などが義務付けられます。さらに、特定荷主・特定連鎖化事業者には、CLO（物流統括管理者）の選任も求められます。

この制度の重さは、「物流部門が書類を作ること」ではなく、「物流を経営判断として扱うこと」にあります。

CLOが機能すれば、物流は単なるコスト削減対象ではなくなります。荷待ち時間を減らし、積載率を上げ、部門間の無理な調整をほどくことで、限られた輸送力を事業成長に振り向けられるようになります。物流の効率化は、守りの法対応であると同時に、企業のビジネスを前に進める攻めの経営テーマでもあります。

では、CLOに選ばれた人は何をすればよいのか。

国の様式はあります。制度説明もあります。先進企業の事例もあります。けれど、実務で最初に詰まるのはおそらくここです。

> 自社の状況だと、どの施策を選ぶべきなのか。
> その施策は、本当に実行できるのか。
> 社内で説明できる数字と根拠はあるのか。

この問いに答えるために、Logi-Intel Dashboard というCLO支援アプリケーションを個人開発しています。

Logi-Intel Dashboardは、物流DXを実行する現場ツールではなく、CLOが物流課題を経営判断に変換するための意思決定支援アプリケーションです。

この記事では、物流・SCM担当者、CLO候補者、営業・企画・経営層に向けて「何を支援するアプリなのか」を説明しつつ、エンジニア向けにMCPや成果物生成の設計も紹介します。

## なぜ作ったか

きっかけは、LLMを使ったアプリケーション開発の成果を、もう少し実務に近い形で展開したかったことです。

個人的に、データを集め、分析し、そこから次のアクションや意思決定につなげる流れが好きです。単に画面を作るだけではなく、数字や根拠をもとに「では何をすべきか」を考えられる作業に価値を感じます。アプリケーションそのものに惹かれるというより、その作業に価値を見出し、実務で使える形に落とし込めるところに面白さがあります。

その観点で見ると、CLO支援はかなり面白い題材でした。

- 公的データを使える
- 法令や制度に基づく判断がある
- 自社データと外部データを組み合わせる必要がある
- 最終的には施策選定や社内説明につなげる必要がある

また、私は物流システムの開発に携わっているため、課題として身近でもありました。物流DXツールはありますが、CLOが「どの施策を優先すべきか」を決めるところまで支援するものは、少なくとも身近には見えていませんでした。

そこで、CLO支援を入口にした「物流課題を経営判断に変換するアプリ」を作ってみることにしました。

## 物流・CLO担当者向け: 何を支援するのか

CLOは、物流現場だけを見る役職ではありません。

営業が短納期を求める。生産が効率のよいロットを優先する。調達や在庫管理がそれぞれ別の制約を持つ。そうした部門ごとの最適化が、物流にしわ寄せされる。CLOの仕事は、この構造を経営判断として調整することです。

経済産業省のCLO取組事例集を読むと、先進企業の取り組みも同じ方向を向いていました。

- SUBARUは、部門に分散していた物流費を全社で把握できるようにした
- J-オイルミルズは、物流ハンドブックを作って他部門への説明に使った
- 日清食品は、異業種・同業他社との共同輸送を進めた
- 日本アクセスは、待機時間の可視化と営業部門を巻き込んだ改善に取り組んだ
- サンゲツは、積載効率だけでなく荷役負荷の低減も含めて判断した

こうした事例は大企業の先進的な取り組みに見えますが、CLOの選任が義務となる企業にとっても、目指す方向は同じです。物流を部門ごとの個別最適のまま扱うのではなく、全社の経営効率化につながるテーマとして整理し、どこから着手すべきかを判断できるようにする必要があります。

ここから見えるのは、CLO支援アプリが単なるダッシュボードでは足りないということです。必要なのは、データを見せることではなく、部門間・社外・経営層との会話に使える判断材料を作ることです。

Logi-Intel Dashboardでは、主に次の機能を想定しています。

| 機能 | 目的 |
| --- | --- |
| 適用判定 | 自社が特定第一種荷主・特定第二種荷主・特定連鎖化事業者などに該当するかを確認する |
| 入力テンプレート生成 | 自社データ入力用のExcelフォーマットをダウンロードし、記入後に分析へ使えるようにする |
| 業界ベンチマーク | 自社の業種・地域を、e-Statなどの公的データや標準係数と比較する |
| ドライバー需給ギャップ | 公的統計をもとに地域別の物流制約を把握する |
| 数値目標提案 | 積載率、CO2、物流コストなどの改善目標を提案する |
| 施策評価 | 施策をROI、実装可能性、法令適合度、補助金観点で評価し、優先順位を決める |
| シナリオ試算 | 燃料価格や需要変動などのストレスをかけて計画の強さを見る |
| 財務翻訳 | 物流KPIを社内説明に使える財務インパクトへ翻訳する |
| 成果物生成 | PowerPoint、Word、Excel、Markdownを一括生成する |
| 提出前検証 | 提出用様式に必要な記載や整合性を確認する |

現時点では、完成したSaaSの発表ではなく、コンセプトと実装途中の共有として書いています。

## 物流・CLO担当者向け: 入力データと公的データ

CLO支援では、分析以前に「企業がどんなデータを準備すればよいか」を明確にする必要があります。

いきなり分析画面を出すのではなく、入力用Excelテンプレートをダウンロードし、会社情報、拠点、取扱貨物量、積載率、荷待ち時間、荷役時間などを整理してから取り込める導線を用意しています。

これは地味ですが重要です。CLO候補者や物流・SCM担当者が最初に困るのは、「どのデータを、どの粒度で、誰に依頼すればよいか」だからです。入力フォーマットがあると、社内で記入依頼しやすくなり、分析に必要なデータ粒度もそろえやすくなります。

もうひとつ重視しているのが、e-Statなどの公的データです。

物流改善の提案は、感覚や思いつきだけでは社内で通りません。地域別の産業構造、事業所数、従業者数、物流制約、法令上の基準など、説明可能な根拠に接続する必要があります。

ただし、公的データを取得して表示するだけでは、CLOの意思決定には届きません。自社の業種、取扱量、積載率、荷待ち時間、投資余力、拠点数、営業部門との調整余地まで考えて、初めて施策選定になります。

流れとしては、次のようなイメージです。

```text
公的データを取る
  -> 自社データと合わせる
  -> 入力テンプレートでデータ粒度をそろえる
  -> 法令上の立ち位置を判定する
  -> 施策候補を出す
  -> 実行可能性で絞る
  -> 事業インパクトに翻訳する
  -> 提出・説明用の成果物にする
```

ここが、単なるデータビューアとCLO支援アプリの違いだと思っています。

## 物流・CLO担当者向け: 施策の優先順位付け

特に重視しているのは、施策の優先順位付けです。

CLOが社内で聞かれるのは、「なぜこの施策をやるのか」だけではありません。

「なぜモーダルシフトではないのか」
「なぜ共同配送ではないのか」
「なぜバース予約から始めるのか」

こうした問いに答えるには、選定理由だけでなく、選外理由も必要です。

そこで施策評価では、候補施策を次のような観点で見ています。

| 評価軸 | 見ていること |
| --- | --- |
| ROI | 投資額に対して、どの程度の効果が期待できるか |
| 実装可能性 | 拠点数、車両、協力会社、社内体制に対して実行できるか |
| 法令適合度 | 中長期計画に必要な項目と結びついているか |
| 補助金・認定制度 | 外部制度と結びつけられる可能性があるか |

ここで重要なのは、スコアを高く見せることではありません。むしろ「この会社には今は難しい」と言えることです。共同配送は魅力的でも、相手先候補やルート条件がなければ絵に描いた餅になります。高度な倉庫自動化も、投資余力や現場標準化がなければ先にやるべきではないかもしれません。

## エンジニア向け: アーキテクチャ

GitHubリポジトリは現時点ではPrivateなので、ここではコード参照なしでも伝わるように、設計の考え方だけ説明します。

アーキテクチャは、分析・法令判定・成果物生成の中核ロジックを中心にして、複数の出口を持つ形にしています。

```text
Open Data APIs / Static Data
        |
        v
Core logic
  Data clients    e-Stat、気象庁、xROAD、燃料価格など
  Legal rules     特定荷主判定、改善基準チェック
  Analytics       ベンチマーク、施策評価、シナリオ試算
  Export          PPT、Word、Excel、Markdown生成
        |
        +--> FastMCP tools / LLMからの自然言語操作
        +--> FastAPI REST
        +--> Next.js dashboard
        +--> outputs/
```

重要なのは、判断ロジックをMCPやREST APIやWeb画面に分散させないことです。施策評価、法令判定、成果物生成のロジックは中核部分に集約し、MCPやREST APIはそこへ到達する薄い入口にしています。

出口が変わっても、CLO支援のロジックは同じであるべきです。ChatGPT、Claude、Gemini、AIコーディングツールのようなクライアントから自然言語で使う人もいれば、Webダッシュボードから触る人もいます。どの入口から使っても、同じ判断ロジックと同じ成果物生成に到達できる構造にしたいと考えています。

## エンジニア向け: MCPを作った理由

このアプリでは、Web画面だけでなくMCPサーバーも作っています。

MCPを使うと、ChatGPT、Claude、Gemini、AIコーディングツールのようなクライアントから、自然言語でCLO支援機能を呼び出せます。たとえば、次のような使い方を想定しています。

```text
sample_manufacturing_01 の中長期計画ドラフトを作って。
施策候補のTop 3と、選ばなかった施策の理由も出して。
社内説明向けのPPTと、根拠数値を追えるExcelも生成して。
```

このときLLMは、単に文章を生成するのではなく、MCPツールを通じて中核ロジックを呼び出します。

主なMCPツールは、CLO支援の流れに合わせて `logi_clo_*` に統一しています。

| MCPツール | 役割 |
| --- | --- |
| `logi_clo_eligibility` | 特定荷主などの該当区分を判定する |
| `logi_clo_benchmark_position` | 業界・地域ベンチマークを見る |
| `logi_clo_driver_gap` | 地域別のドライバー需給ギャップを見る |
| `logi_clo_measure_eval` | 施策を評価し、優先順位を出す |
| `logi_clo_scenario_sim` | 燃料価格や需要変動のストレスをかける |
| `logi_clo_financial_translate` | 物流KPIを経営指標へ翻訳する |
| `logi_clo_plan_draft` | PPT、Word、Excel、Markdownを一括生成する |
| `logi_clo_submission_validate` | 提出前の整合性を検証する |

MCPを作ってよかったのは、プロダクトの使い方を早く試せることです。Web UIを作り込む前でも、LLMに「この会社なら何から着手すべきか」と聞き、内部では実装済みの分析ロジックを呼び出せます。

もうひとつの利点は、MCP経由でもWebと同じ生成物に到達できることです。PPT、Word、Excel、Markdownを生成したあと、その場で「この施策の根拠は何か」「燃料価格が上がった場合はどうなるか」「この施策を外した理由を詳しく知りたい」といった疑問を、会話の流れで深掘りできます。

画面操作だけだと、利用者は用意されたボタンやフォームの範囲でしか探索できません。MCP経由なら、成果物を取得したあとに、根拠、前提、代替案、リスクをインタラクティブに確認できます。CLO支援のように「一回の分析で終わらず、関係者と議論しながら計画を詰める」用途とは相性がよいと感じています。

## エンジニア向け: 成果物生成で苦労したこと

このアプリは、最終的に次のような成果物を出します。

- 社内説明向けPowerPoint
- 様式に沿ったWordドラフト
- 根拠数値と出典を追えるExcel
- 社内共有やレビューに使えるMarkdown

実装上は、成果物生成の責務をひとつの層に集約しています。

画面やAPIは変わっても、成果物の品質は同じであるべきです。CLO支援の価値は、分析ロジックそのものだけでなく、社内でレビューされ、説明され、修正され、提出されるところまで届いて初めて成立するからです。

作っていて一番手間がかかったのも、この成果物品質でした。

Web画面で見ればそれなりに見える情報でも、PowerPointに出すと急に粗が出ます。文字がはみ出す、表が読みにくい、KPIカードの余白が詰まる、ページごとの情報密度が揃わない。Excelも同じで、単に数値を並べるだけではレビュー資料になりません。読み手が最初に見るサマリー、根拠を確認する詳細表、出典を追うシートを分ける必要があります。

Wordはさらに別の難しさがあります。様式に沿う必要があるため、見た目の自由度よりも、必要項目が抜けていないこと、法令区分に応じた文言が崩れないことが重要になります。

LLMを使ったアプリ開発では、画面や文章の生成に目が行きがちです。しかし、CLO支援の文脈では、最後に出てくるPPT、Excel、Wordの品質がそのままプロダクトの信頼性になります。ここは思った以上に地味で、かつ重要でした。

## AWS上の開発用環境

開発用には、次のURLでPoC環境を動かしています。

https://d1zei8qivkf3cr.cloudfront.net/

構成は、PoCとして運用コストを抑えるため、CloudFront、S3、API Gateway、Lambdaを中心にしています。

```text
CloudFront
  +-- S3: Next.js static export
  +-- API Gateway HTTP API
        +-- Lambda: FastAPI
              +-- SSM Parameter Store
```

最初はECSやALBも検討しましたが、開発段階では常時稼働のコストを増やすより、静的配信とサーバーレスで十分だと判断しました。

## 作ってわかったこと

### CLO支援は「法対応アプリ」だけでは弱い

法定様式を埋めるだけなら、入力フォームとWord出力で足ります。

でも、CLOの本当の難しさは、部門間の利害調整と投資判断です。物流部門だけが頑張っても、営業が短納期を変えない、生産がロットを変えない、取引先と調整できない、という状態では改善は進みません。

CLOが活躍する会社では、物流改善は「罰則を避けるための対応」に留まりません。営業が売りやすくなり、調達や生産の計画精度が上がり、配送制約を前提にした現実的な成長戦略を描けるようになります。物流の効率化を、ビジネスを止めないための防衛策ではなく、ビジネスを伸ばすための基盤として扱うことが重要だと考えています。

### 物流DXは、非効率をデジタル化すると逆に危ない

既存の非効率な運用をそのままIT化すると、「デジタル化された非効率」になります。

たとえば、個別最適の納品条件を維持したままシステムだけ入れると、非効率が高速に処理されるだけです。CLOに必要なのは、業務を標準化し、全体最適に寄せる判断です。

### 出典と説明責任は機能の一部

物流改善の数値は、社内説明や関係部門との合意形成で必ず突っ込まれます。

「そのドライバー不足の数字はどこから来たのか」
「CO2削減量の係数は何か」
「この施策の効果は楽観的すぎないか」

そのため、出典URL、統計表ID、告示・法令との対応を追えるようにすることは、単なる親切機能ではありません。CLOが説明責任を果たすための本体機能です。

### CLO対象企業に求められることは多い

CLOの選任が義務となる企業には、単に担当者を置くことだけが求められているわけではありません。

特定荷主や特定連鎖化事業者に該当する場合、指定に関する届出、中長期計画の作成、物流統括管理者であるCLOの選任、定期報告などが必要になります。中長期計画では、貨物重量の増加、荷待ち時間の短縮、荷役等時間の短縮といった取り組みを整理し、実施時期や目標も示す必要があります。定期報告では、判断基準の遵守状況や荷待ち・荷役等時間の状況なども継続的に報告します。

つまりCLO支援で必要なのは、法定様式を作るだけではありません。自社がどの区分に該当するのか、どのデータを集めるべきか、どの施策を優先すべきか、社内や取引先と何を合意すべきかを、継続的に判断できる状態にすることです。このアプリで入力テンプレート、施策評価、成果物生成、出典管理をまとめて扱いたい理由もそこにあります。

## これからやること

今後は、開発中の検証として実際のCLO候補者や営業担当者に触ってもらい、次の点を検証します。

- 入力項目は、現実の企業が準備できる粒度になっているか
- 入力テンプレートは、物流・SCM担当者が社内で記入依頼しやすい形になっているか
- 施策推薦は、現場感とズレていないか
- PowerPointは、社内説明でそのまま使える品質か
- Wordドラフトは、社内確認から提出準備まで進められる形か
- 社内外の調整、S&OP、共同配送など、次の機能拡張に何を優先すべきか

## まとめ

CLO選任義務を含む物流効率化法の規制的措置は、単に物流担当者の仕事が増える話ではありません。

物流を、コスト削減の対象から、経営の持続可能性を支える意思決定領域へ移す制度変更だと思っています。

CLOが社内で機能すれば、物流効率化は事業の制約を減らし、企業の成長余地を広げる取り組みになります。

Logi-Intel Dashboardで作りたいのは、データを眺めるダッシュボードではなく、CLOが物流課題を経営判断に変換するための判断材料と成果物を作るアプリです。

技術的には、Python、FastAPI、MCP、Next.js、AWSを組み合わせた素直な構成です。ただし、価値の中心はそこではありません。

法令、公的データ、社内データ、施策評価、財務翻訳、成果物生成をひとつなぎにし、CLOが施策の優先順位を決められるようにすること。

そこに、CLO支援アプリとしての面白さがあります。
